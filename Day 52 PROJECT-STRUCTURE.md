```
healthedge-capacity-intelligence/
├── index.html              # Main dashboard SPA (KPIs, charts, table,
│                            #   Scenario Planner, ICU Module, Volumes)
├── login.html               # Login screen, wired to Firebase Auth
├── firebase-config.js        # Firebase project connection details
│                            #   (from Firebase console; safe to be public —
│                            #   real protection is Security Rules, not secrecy)
│
├── data/                    # Source-of-truth JSON, one file per city.
│   ├── dubai.json            #   Used for local dev/testing and as the
│   ├── abudhabi.json         #   upload source for the Firestore 'regions'
│   ├── riyadh.json           #   collection (Day 5). Not fetched directly
│   ├── jeddah.json           #   by the live app after Day 5 — Firestore
│   └── dammam.json           #   is the live source of truth from then on.
│
├── scripts/                  # One-off Node/JS utility scripts, not part
│   └── validate-data.js       #   of the shipped app. Loops all 5 JSON files
│                              #   and flags missing/invalid fields (Day 4).
│
├── assets/                   # (if/when needed) static images, icons —
│                              #   kept separate from logic files.
│
├── .firebaserc                # Firebase CLI project alias (auto-generated
├── firebase.json              #   by `firebase init hosting`, Day 10)
│
├── .gitignore                 # Excludes any local-only files (e.g. OS files)
└── README.md                  # Project overview, setup steps, live URL
```

## Folder Responsibilities

| Path | Responsible for | Why structured this way |
|---|---|---|
| `/index.html` | All dashboard UI + logic (single file, per the "no framework" stack decision) | Keeps the whole app in one deployable artifact; matches Day 15 template it extends |
| `/login.html` | Standalone auth screen | Kept separate from `index.html` so the auth check can gate access before any dashboard code/data loads |
| `/firebase-config.js` | Firebase SDK initialization | Isolated so it's easy to find/update the connection config without touching app logic |
| `/data/*.json` | Canonical, human-readable dataset | Serves as the editable "master copy" during Days 2–4; Firestore is populated *from* these files, not the other way around, so there's always a plain-text backup outside the database |
| `/scripts/validate-data.js` | Data-quality checks | Kept out of the deployed app (not loaded by `index.html`) — it's a developer tool, not a runtime dependency |
| `/assets/` | Static media | Reserved for future icons/images; empty in v1.0 if the template is CSS-only |
| `firebase.json`, `.firebaserc` | Deployment configuration | Auto-generated by the Firebase CLI on Day 10; committed so redeploys are reproducible |

## Where Future Code Will Live

- **New dashboard sections** (e.g., future emirates, payment tiers from PRD Section 11) → new collapsible sections inside `index.html`, following the existing card pattern; if the file grows unwieldy, a natural v1.1 refactor is splitting `<script>` logic into `/js/*.js` modules — deliberately not done in v1.0 to avoid premature complexity.
- **New data fields** → extended into the `data/*.json` schema and mirrored in `SCHEMA.md`; validated by an updated `scripts/validate-data.js`.
- **Any future server-side logic** (e.g., live data sync, multi-workspace accounts) → would live in a new `/functions/` directory using Firebase Cloud Functions, kept out of v1.0 by design.

## Why This Structure Was Chosen

1. **Matches the "no framework" decision** — a flat structure is appropriate for a small number of static files; a `/src`, `/components`, `/public` split would imply a build step that doesn't exist here.
2. **Separates data from code** — `/data` can be edited, validated, and diffed in Git independently of UI changes.
3. **Separates developer tools from shipped code** — `/scripts` never ships to Firebase Hosting, keeping the deployed bundle minimal.
4. **Everything Firebase needs stays at the root** — `firebase.json`/`.firebaserc` must live at the project root by Firebase CLI convention.
